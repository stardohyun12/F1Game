## 0. 게이트 6/10 이 말하는 것 (내가 직접 연 파일)
`art/_review/2026-10-23-cargo-box/visual-gate.md`, `compare.png` [확인]
- 결함: ① 옆면 표식이 십자가처럼 읽힘 ② 넓은 단색 면·드문 사각 얼룩 = 원화의 촘촘한 명암보다 단조 ③ 축소 화면에서 흰 숫자판만 읽히고 상자·테이프는 탁함. "같은 게임의 택배 상자처럼 보이는가: 아니오."
- PD 가 적은 "12 tris 정육면체라 기본 큐브로 읽힘"은 게이트 문서에는 없다(게이트는 *이미지만* 봤다). 12 tris 는 `compare.png` 캡션. 원인 가설로 다루되 게이트가 확인한 건 아니다.
- 상자 한 변 0.4m. 텍셀 밀도 32.5~33.3px/m(compare.png 캡션) → **한 면 가로 약 13 텍셀**. 1280×720 블렌더 렌더에서 상자는 약 59×52px.

**[측정] 기준 원화는 진짜 픽셀 격자가 아니다.** `art/concept/lofi-styles-2026-10-13/02_warm_street.png`(1672×941)에서 열 경계 신호를 주기 3~15 로 겹쳐 봤다 — 어느 주기도 격자 신호가 없다(최대/평균 1.01~1.07, 격자면 크게 튀어야 함). 즉 원화의 "픽셀"은 AI 가 흉내 낸 것이라 블록 크기가 제각각이다. 따라서 **"원화와 같은 밀도"는 맞출 격자가 없다** — 우리가 격자를 *정해야* 한다(아래 3절). 이건 지난 보고의 "가짜 픽셀" 가설과도 맞는다.

### "수작업 같은" 느낌을 만드는 것 — 확인된 것 vs 추정
- **[확인 3곳이 같은 말]** 디테일을 폴리가 아니라 **텍스처에** 둔다(EDC, Visceral Carnage, Dusk 의 "텍스처 위주"). 12 tris 자체가 문제가 아니라, **12 tris 인 채로 텍스처마저 비어 있는 것**이 문제.
- **[확인]** 소품(사람이 만지는 물건)은 **손 픽셀**, 배경 면은 **사진 기반**(EDC). Dusk 는 둘을 섞음.
- **[확인]** 해상도를 낮추면 디테일링이 *쉬워진다*(Visceral Carnage) — 저해상도 + 한정 팔레트 + **손으로 얹는 층(스탬프·노이즈)** 조합.
- **[확인]** 단색 면은 *노이즈/디더 층을 따로 얹어* 깬다(Visceral Carnage 블루노이즈).
- **[확인]** 포인트 필터 + 한정 팔레트 + 엔진의 "좋아 보이게 하는 기능"을 꺼서 일관성 확보(Dusk).
- **[추정]** 버텍스 컬러/굽기 AO: 튜토리얼들이 PS1 룩의 구성요소로 든다. 그러나 이번에 읽은 *개발자* 원문 3곳에는 없다 → "필수"라 단정 못 함.
- **[추정]** 저해상도 렌더/디더 후처리가 "수작업 같은 느낌" 자체를 만드는지는 근거 없음. 후처리는 *이질감을 덮는* 효과이지 에셋 품질을 올리는 효과가 아니라고 보는 게 안전.

## 2. "실물감" 최소 요소 — 일상 소품 체크

**근거 한계**: "택배 상자가 진짜처럼 읽히려면"을 직접 다룬 개발자 글은 못 찾았다. 검색 결과는 제품 설명뿐: 저폴리 상자 팩은 **132~288 tris**, 접힘·마모 표시, **크기가 다양**한 상자 세트 [2차: Superhive/Unity Asset Store 목록]. 아래 표는 **일반 제작 상식 = [추정]**, 우리 게이트 결함과 맞춰 정리했다.

| 요소 | 상자 | 케이크·계란판·병·생선 응용 [추정] | 이번 게이트와의 연결 |
|---|---|---|---|
| **실루엣 불규칙** | 윗면 뚜껑 두 장 + 틈, 가운데가 아주 조금 처짐, 한 모서리 살짝 눌림 | 계란판: 30구 돌기 실루엣(윗면 요철이 곧 정체). 와인: 어깨·목 곡선 한 번. 생선: 꼬리·지느러미 | "기본 큐브로 읽힘" |
| **모서리** | 윗 가장자리에 chamfer(뚜껑 접힘) — 실루엣에 보이는 곳만 | 케이크 상자 손잡이 끈 | 폴리 예산: 같은 곳에서 읽은 글(Polycount)은 "모서리 둥글림은 *실루엣에 보일 때만*" [2차: https://polycount.com/discussion/comment/2766303] |
| **인쇄물 비례** | 송장 라벨은 상자 면 전체가 아니라 **작은 부분**(ISO A6 = 105×148mm 가 흔한 상한, 확인된 규격값. 한국 택배 송장 크기는 [미확인]). 400×300mm 면에서 A6 는 폭의 약 26% | 와인 라벨·계란 도장 | "큰 흰 라벨이 표지판" — **이 상자의 숫자판은 면의 큰 부분을 덮는다** |
| **색 변화** | 같은 갈색 안에서 면마다 명도 차(윗면 밝고 옆면 어둡고 접지면 어둡다), 테이프는 *다른 재질색*(더 노랗고 반질) | 케이크 상자 흰색+포인트 한 색 | "넓은 단색 면" |
| **마모의 이유** | 모서리·접지면·테이프 가장자리 | 계란판 눌린 곳 | 지난 보고 규칙 6 과 동일 |
| **사이즈 변주** | 같은 상자라도 인스턴스마다 ±수 % 치수·텍스처 오프셋 | — | 같은 상자 반복 시 "복붙" 인상 |

**텍셀 한계 [측정+추정]**: 32px/m 에서 A6 라벨 폭 105mm = **약 3.4 텍셀**, 높이 148mm = 약 4.7 텍셀 → 글자·로고는 *읽을 수 없다*. 그래서 현재 상자는 숫자판을 크게 키웠고(→ 표지판처럼 읽힘). **라벨을 실물 비례로 줄이려면 화물 텍셀 밀도를 올려야 한다**(아래 규칙 6).

## 3. 화면 전체: 저해상도 렌더 + 포인트 업스케일 (+팔레트/디더)

### 3-1. 이 프로젝트의 현재 상태 [확인: 파일 열어봄]
- Unity 6000.3.19f1, URP 17.3.0 (`F1/ProjectSettings/ProjectVersion.txt`, `Packages/manifest.json:10`).
- `F1/Assets/Settings/PC_RPAsset.asset:29-30` → `m_RenderScale: 0.5`, `m_UpscalingFilter: 2`. (2 = Point 로 읽는 것은 URP enum 순서 Auto/Linear/Point/FSR/STP 에 의한 **[추정]** — 에디터에서 한 번 눈으로 확인 필요.) Mobile 은 0.8 / 0.
- 카메라는 `renderPostProcessing = true` 로 설정되는 에디터 스크립트가 다수(`ArtCapture.cs:63`, `CoastalNoonLook.cs:60`, `ApplyDioramaLook.cs:104`), 볼륨 `PitCrewPostFX` 에는 ColorAdjustments(대비 18·채도 22)·Vignette 가 있다.
- **충돌 가능성 [확인: Unity 6.6 문서]**: Upscaling Filter "Nearest-Neighbor" 항목에 **"Post-processing 이 켜져 있으면 동작하지 않는다"**. 문서는 6.6 이고 프로젝트는 6000.3 — 같은지 **[미확인]**. 즉 *이미 켜 둔 0.5 + 포인트가 실제로 포인트로 나오는지* 부터 검증해야 한다. https://docs.unity3d.com/Manual/urp/universalrp-asset.html
- Render Scale 은 **게임 렌더만** 스케일하고 UI 는 네이티브 해상도 [확인, 같은 문서].

### 3-2. 해상도 선택 계산 [측정+추정]
조건: `FollowCamera.cs` 오프셋 (0,3,-6) → 차까지 약 6.7m, `baseFov = 50`(세로, Unity 기본). 화면 세로 시야 = 2·6.7·tan(25°) ≈ 6.25m.

| 렌더 높이 | 화면 px/m (차 거리) | 화물 텍셀 32/m 와의 비 | 상자(0.4m) 폭 |
|---|---|---|---|
| 270 (480×270) | 약 43 | 화면 1px ≈ 0.75 텍셀 → **텍셀 격자≈화면 격자** | 약 17px |
| 360 (640×360) | 약 58 | 화면 1.8px/텍셀 | 약 23px |
| 540 (960×540, 현재 0.5×1080p) | 약 86 | 2.7px/텍셀 | 약 35px |

해석 [추정]: 480×270 이면 *화면 한 칸과 텍셀 한 칸이 거의 같은 크기*가 돼 "픽셀 격자 하나" 원칙이 자동으로 지켜진다. 960×540 에서는 텍셀이 화면에서 2~3칸 블록으로 보여, **에셋마다 텍셀 밀도가 조금 달라도 그대로 드러난다**. 단 카메라 거리·FOV(속도에 따라 maxFov)에 따라 달라지고, 상자 17px 폭은 *더 작아진다는 뜻*이라 소품 가독성에 불리 → 화물은 더 키우거나 대비를 올려야 한다. **실제 화면으로 3종 비교가 필요하다.**

### 3-3. 얼마나 이질감을 덮는가
- **근거 없음/제한적**: 이 효과를 정량한 자료는 못 찾았다. 확인된 건 Lethal Company 의 낮은 내부 해상도(860×520)가 룩의 일부이고 *부작용으로 깜빡임*이 있다는 것 [2차], EDC 가 456×256 가상 화면 기준으로 설계했다는 것 [확인].
- [추정] 저해상도는 (a) 서로 다른 텍셀 밀도의 차이를 화면 격자로 *통일* (b) 가는 노이즈·잔디테일을 *지움* → 지난 조사의 AI 단서(의미 없는 디테일)를 줄인다. 그러나 (c) **형태 문제(큐브로 읽힘)·구도 문제는 덮지 못한다** — 오히려 17px 폭에선 실루엣이 더 중요하다.
- 팔레트/디더 포스트: **Dusk 는 팔레트를 *텍스처에서* 줄였고**, Visceral Carnage 는 디더를 *텍스처 단계에서* 굽는다(둘 다 화면 후처리가 아님) [확인]. 화면 디더는 카메라가 움직일 때 패턴이 헤엄친다는 지적이 흔하나 *이번에 읽은 원문 근거는 없다*[추정]. 우리는 이미 공용 32색을 텍스처에 쓰므로 화면 팔레트 후처리는 이중 적용이 된다.

### 3-4. Unity URP 에서 구현·비용
| 방법 | 내용 | 비용·위험 |
|---|---|---|
| **A. URP Render Scale + 업스케일 필터 = Nearest** | 이미 있음(0.5). 480×270 은 1080p 기준 0.25. 해상도가 창 크기에 비례(고정 해상도 아님) → 1080p 가 아니면 비정수 배율 | 코드 0줄. 화면 픽셀 수 960×540→480×270 은 **1/4**(1080p 대비 1/16). 성능은 **실측 안 함**. 위 "후처리 켜면 NN 안 됨" 확인 필요 |
| **B. 저해상도 RenderTexture(Point) → 화면에 정수 배 블릿** | 카메라를 작은 RT 로 렌더하고 UI 카메라로 올림. 포럼·UPixelator 가 이 방식 | URP 17(Unity 6)은 **Render Graph 로 새로 짜야** 하고, 이 스레드의 코드는 URP 14 시절이며 작동 미확인 [2차: https://discussions.unity.com/t/low-resolution-rendering-3d-pixel-art-with-integer-upscaling/848462 · https://discussions.unity.com/t/pixelize-effect-in-urp/925213]. **Unity 6 에서 후처리와 함께 검증된 예는 못 찾음** |
| **C. 커스텀 풀스크린 패스(UV 양자화)** | 위 스레드 한 사람이 "더 싼 꼼수"로 언급 | 진짜 저해상도 렌더가 아니라 성능 이득 없음 [2차] |

→ 시도 순서 [추정]: **A 로 3종(480×270 / 640×360 / 960×540) 캡처 → 도현 판정**. A 에서 포인트가 안 나오면 후처리(볼륨 색보정)를 *끄고* 색보정은 텍스처·LUT 로 굽거나, 그때 B.
- 보정 포인트 [확인(문서)/추정]: 카메라 이동 시 "픽셀 기어다님(pixel creep)"은 서브픽셀 카메라 오프셋으로 푸는 방법이 있다(UPixelator) — 우리에겐 나중 문제.
- UI: Render Scale 에서 UI 는 네이티브 해상도 [확인]. Galmuri 폰트는 정수 배율 규칙(지난 브리프 규칙 3)을 UI 쪽에서 따로 지킨다.

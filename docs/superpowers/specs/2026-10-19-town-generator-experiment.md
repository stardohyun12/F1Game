## 1. 플레이어 경험 목표
**"진짜 지중해 항구 마을 골목을 실제 크기 F1 차로 배달하는데, 마을 안 한 번의 배달이 1~2분 걸린다."**

나왔다는 걸 아는 방법:
- 도현이 두 결과의 톱다운·운전 시점 그림을 보고 "실제 마을처럼 보이는가"를 판정한다(§7 A9). AI 는 이걸 판정하지 않는다.
- QA 합성 주행으로 마을 구간 한 판 시간이 기준선 10~21초에서 §7 A5 목표로 늘어난 것을 숫자로 확인한다.

이 실험의 산출물은 "이긴 쪽"이 아니라 **도현이 고를 수 있는 같은 조건의 두 결과**다(D-108). 한쪽만 고를지, 마을마다 다르게 쓸지는 도현이 정한다.

## 2. 구조 — 앞단 둘, 뒷단 하나
```
[앞단 A: OSM]  Overpass 원본(아말피 항구 조각 + 포지타노 비탈 조각) → 선형 도로망(JSON)
[앞단 B: roadgen] 시드 + 같은 고도맵 + 인구밀도맵 → 선형 도로망(JSON)
                         │  (둘 다 같은 "선형 도로망 JSON" 형식으로 내보낸다, §4.1)
                         ▼
[공통 뒷단]  ① 도로 등급 매핑 → ② 보행로 승격 규칙 → ③ 칸 스냅 → ④ 정리(막다른 가지·평행선)
            → ⑤ roadMask/heightMask + 폴리라인 보존 → ⑥ D-100 규칙 검사 → ⑦ 배달지 11 배치
            → ⑧ 연결성 검사(TrackConnectivityVerifier) → ⑨ 실험 씬 설치 → ⑩ 비교 그림
```
- 공정성의 핵심: **뒷단 ①~⑩은 한 벌의 코드**로 두 앞단에 똑같이 적용한다. 앞단마다 따로 튜닝 금지.
- 앞단은 서로 독립 → 프로그래밍팀이 병렬로 만들 수 있다(뒷단 먼저, 형식 §4.1 고정 후).

## 4. 공통 뒷단 규칙

### 4.1 선형 도로망 JSON (두 앞단의 출력 형식)
```json
{ "source": "osm|roadgen", "seed": 0, "bounds_m": [480, 400],
  "segments": [ { "id": 1, "class": "major|minor|alley|footway|steps|path",
                  "points_m": [[x,z],[x,z],...] } ],
  "landmarks_hint": [[x,z]] }
```
- 좌표는 미터, 원점 = 땅 남서 모서리, +z = 북(바다 반대).
- OSM 등급 → class: primary/secondary/tertiary → `major` · residential/unclassified/living_street/service → `minor` · pedestrian → `alley` · footway → `footway` · steps → `steps` · path·track 등 → `path`.
- roadgen 등급 → class: highway → `major` · street → `minor`. (roadgen 은 alley·footway·steps 를 만들지 않는다.)

### 4.2 보행로 승격 규칙 (게임 추상화의 핵심)
실제 아말피형 마을은 길의 82~83% 가 계단·보행로다(조사 노트 실측). 그대로 쓰면 차가 갈 길이 거의 없다.
| class | 게임 도로 | 조건 |
|---|---|---|
| major | 큰길(2차로) | 항상 |
| minor | 골목(1차로) | 항상 |
| alley | 골목(1차로) | 항상 승격 |
| footway | 골목(1차로) | **승격 조건 둘 중 하나**: (a) 연결성 — 승격하지 않으면 도로 조각이 고립됨 (b) 우회로 — D-100 ② 평지 우회로가 이 footway 로만 생김. 그리고 길이 ≥ 2칸 |
| steps | 도로 아님 | 차가 못 가는 계단. 칸은 "계단 장식 후보"로만 표시(아트 범위 밖) |
| path | 버림 | — |
roadgen 은 footway 가 없으므로 (a)(b) 승격이 발생하지 않는다. 그 차이 자체가 비교 결과다.

### 4.3 칸 스냅·정리
1. 폴리라인을 8m 칸에 래스터화: 4방향 연결만(대각선은 계단식 2칸), 선 굵기 1칸.
2. 칸 사이 경사 > 12% 인 도로 칸 연결은 끊는다(§3).
3. 막다른 가지 길이 < 2칸은 제거. 단 배달지·출발점 칸은 남긴다.
4. 1칸 간격으로 평행한 두 줄은 한 줄로 합친다.
5. 끊긴 조각은 가장 가까운 큰 조각에 칸 A*(경사 비용 = 거리×(1+k·경사²), k 가설 20)로 잇는다. 잇기에 쓴 칸 수를 보고에 남긴다(앞단 품질 지표).
6. 원본 폴리라인은 버리지 않고 `polylines.json` 으로 보존(해안도로 P1 의 스플라인 층 입력, 이번 실험은 톱다운 그림 오버레이에만 사용).

### 4.4 배달지 11곳 배치
- 도로 칸 위에만, 서로 3칸 이상 떨어지게.
- 출발점에서의 **도로 경로 거리**(BFS × 8m)로 정렬해 근·중·원이 고르게 섞이도록 배치: 가까움(80~200m) 3 · 중간(200~400m) 4 · 멂(400m 이상) 4. (가설)
- 카탈로그 3잡 라벨은 거리 단계를 고정: **Depot = 멂, FactoryA = 중간, ContainerYard = 가까움.** 이유: 지금 보상 Depot ₩1800 / FactoryA ₩900 / ContainerYard ₩500 이 거리 순서와 맞게 된다(기준선 게이트 기획 차이 ③). 나머지 8 라벨은 남은 자리에 고르게.
- D-100 ③ 랜드마크 자리와 겹치면 랜드마크 옆 칸으로.

### 4.5 D-100 생성 규칙 셋 — 검사로 박는다
| 규칙 | 기계 검사 |
|---|---|
| ① 언덕은 절대 막지 않는다 | 모든 도로 칸 연결의 경사 ≤ 12% (스냅 2단계가 보장, 검사기가 재확인) |
| ② 언덕마다 평지 우회로 하나 | 경사 > 5% 구간을 포함하는 배달지 경로마다, 그 구간 양 끝을 잇는 **모든 연결 경사 ≤ 2%** 대체 경로가 존재하고 길이 ≤ 원래의 2배. 미충족 구간 수를 보고 |
| ③ 꼭대기엔 랜드마크 | 위 마을 단계의 최고 지점 근처 도로에서 1칸 안에 랜드마크 자리 1개 이상(placeholder 큐브, 아트 범위 밖) |

## 6. 앞단별 요구

### 6.1 앞단 A — OSM (D-107: 아말피 항구 + 포지타노 비탈 섞기)
- 원본: Overpass API `way["highway"]` 두 상자 — 아말피 항구 쪽 조각, 포지타노 비탈 쪽 조각. 원본 응답을 날짜와 함께 `tools/town-gen/osm/` 에 캐시(Overpass 는 오늘 실제로 502·406 을 냈다 — 재생성 때 서버에 의존하지 않게).
- 섞는 법: 아말피 조각(240×100m 내외)을 남쪽 항구 띠에, 포지타노 조각(480×300m 내외)을 북쪽 비탈에 놓고, 두 조각 경계는 §4.3-5 의 A* 잇기로 연결. 실제 미터 그대로(D-103 실제 치수와 같은 축척) — 확대·축소 금지.
- 해안도로 SS163 구간은 major 로 들어오며 남쪽 변을 따라간다.
- 라이선스: 크레딧에 "© OpenStreetMap contributors", 가공 roadMask 는 ODbL 로 공개(D-107 수용). 파일 `tools/town-gen/osm/LICENSE-ODbL.md` 에 출처·가공 내용 기록.

### 6.2 앞단 B — roadgen (pboechat/roadgen, MIT)
- **선행 30분 타임박스(E0)**: Unity 6000.3.19f1 에서 roadgen 스크립트가 컴파일되는지. Editor 전용 어셈블리(`F1/Assets/Editor/ThirdParty/roadgen/` + asmdef Editor only)에 LICENSE 와 함께 둔다(배포 빌드에 안 들어감).
  - 30분 안에 컴파일 실패 → **watabou Village Generator GeoJSON 으로 대체**: 브라우저에서 export 1회(수동 1회, 기록 남김) → 같은 JSON 형식으로 변환. 대체 사실을 결과 보고 첫 줄에.
- 입력: §3 의 같은 고도맵(ITerrain 구현), 인구밀도맵 = 항구 쪽 높고 비탈 위로 갈수록 낮게. 시드 5개.
- 출력 세그먼트를 §4.1 JSON 으로 덤프(roadgen 자체엔 파일 export 가 없음).

### 6.3 고도맵 (공통)
- OSM 에는 고도가 없다. **Copernicus DEM GLO-30**(30m 해상도, 무료, 상업 사용 가능·출처 표기 필요 — 정확한 표기 문구는 **미확인**, 구현 전 확인) 에서 같은 두 상자를 잘라 섞는다.
- 다운로드가 막히면: 손 고도맵(남쪽 0m → 북쪽 위 마을 단계, 계곡 1) SO 로 대체하고 보고에 표시.
- 두 앞단이 **같은 파일**을 쓴다. 고도맵은 3단 양자화 후 칸 heightMask 로.

## 7. 수용 기준 (QA·기획이 그대로 테스트로 옮긴다)
각 기준을 **두 결과(OSM, roadgen) 각각** 판정한다. "가설" 표시 수치는 미달이어도 실험은 유효 — 미달 사실을 숫자로 보고하고 도현 판단 재료로 쓴다. 표시 없는 것은 필수.

| ID | 기준 | 측정 방법 |
|---|---|---|
| A1 | 연결성: 도로 칸 전체가 출발점에서 도달 가능, 고립 0 | `TrackConnectivityVerifier` 출력 reachable == total |
| A2 | 배달지 11곳 모두 도로 칸 위·도달 가능, 서로 3칸 이상 | IsRoad 전수 + BFS |
| A3 | 배달지 거리 분포(가설): 출발점→배달지 도로 경로 거리 최소 ≥ 80m · 중앙값 200~350m · 최대 ≥ 450m | BFS × 8m, 11개 표 |
| A4 | D-100 ①②③ 검사 통과. ② 미충족 구간 수 = 0 (가설: 0이 안 되면 수를 보고) | §4.5 검사기 출력 |
| A5 | 한 판 시간(가설): QA 기준선과 **같은 합성 주행 정책**(`docs/qa/tools/synthetic-drive.cs.txt`)으로 ContainerYard·FactoryA·Depot 3런. 중간(FactoryA) elapsedSec 45~120초, 먼 곳(Depot) ≥ 90초. 기준선 10.1~20.7초와 나란히 표기 | `runs.csv` 3줄 |
| A6 | 실제 크기 차 통과성: A5 3런 동안 "속도 0이 2초 이상 지속" 0회(벽·연석 끼임 없음), 성공 3/3 | 주행 로그 |
| A7 | 결정성: 같은 시드·같은 OSM 캐시로 두 번 생성 → roadMask 해시 동일 | 해시 2개 비교 |

## 8. 기술 요구
- **씬**: 메인 `ComplexTrack.unity` 를 덮지 않는다. 복사본 `ComplexTrack_TownOSM.unity`, `ComplexTrack_TownRG.unity` 에 설치. 설치 뒤 세션32 복원 체인(시스템 8개 + OrderBoard 배선)과 **Zones 배선(BUG-002 수정분)** 이 복사본에 들어 있는지 A8 로 확인.
- **코드 위치**: 앞단·뒷단 모두 Editor 전용. 오프라인 스크립트(Overpass·DEM 다운로드)는 Node.js 또는 Python(`py`) 으로 `tools/town-gen/`. 메뉴 `PitCrew/TownGen/Generate OSM`, `Generate RoadGen`, `Verify`, `Capture Compare`.
- **데이터**: 결과는 `TrackLayout`/`CoastalTownLayout` SO 새 에셋 2개(기존 SO 수정 금지, asset.md "레이아웃은 SO"). roadMask 수정이므로 `TrackConnectivityVerifier` 자동 실행 의무(asset.md).
- **결정론**: 필요(A7). 저장: 생성 결과는 SO 로 저장, 런타임 생성 없음. 성능: 측정만(FPS 를 A9 운전 시점 캡처 시 함께 기록), 판정 기준은 이번엔 없음.
- 플랫폼: Windows, Unity 6000.3.19f1.

## 9. 아트 요구

- 차: 실험 씬 한정 균일 스케일 대역(§5). 진짜 실물 크기 F1 모델은 별도 아트 태스크(D-106 원화 먼저), 이 스펙의 §5 표가 그 근거.
- 랜드마크·계단 장식: placeholder 큐브/표시만. 아트는 이긴 쪽이 정해진 뒤.
- 비교 그림 나란히 보기 HTML 은 아트팀 비교 시트(`art/_compare/2026-10-19-scale/index.html`) 형식 재사용 — 판정 순서 1× → 흑실루엣 → 4×.

# PitCrew 스튜디오 — 에이전트 팀 설계 (Agent Studio Team)

> 작성 2026-05-26 · 세션 33 · 도현 승인 후 박음
> 한 줄 요약: **켜진 건 2개(나=허브 / PM=별도 터미널)뿐, 나머지 직군은 일회용 서브에이전트.** 게이트(판정)는 일부러 백지(컨텍스트0), 리드(제안)는 메모리 파일로 부활. 연속성은 켜진 머릿속이 아니라 파일에.

---

## 1. 왜 (동기)

지금 운영 모델은 "역할 분리 게이트"(세션 32, `project_rules/roles.md`) — 코딩(나)은 기획·그래픽 게이트가 통과시키기 전엔 커밋 못 함. 게이트(판정)는 작동한다. 하지만 세 가지가 비어 있다:

1. **내가 병목** — 모든 걸 내가 직접 직렬로 처리. 능동적으로 병렬로 일하는 직군이 없음.
2. **기획 공백** — "다음 뭐 만들지"를 능동 제안하는 디렉터/기획자가 없음. 도현이 매번 방향을 줘야 함.
3. **하네스 자체 발전** — 이 운영체계(B축)를 키우는 게 모두창업 산출물의 핵심인데, 발전을 전담하는 자리가 없음.

이 설계는 게이트 모델을 **버리지 않고 계승**하면서 위 셋을 메운다.

## 2. 핵심 원리

### 2-1. 상주 ≠ 영원히 켜진 머릿속
"상주 직원"은 한 프로세스가 모든 걸 컨텍스트에 들고 영원히 켜져 있는 게 아니다(컨텍스트 한계로 불가능). 대신:

```
직원이 일할 때마다:
1. (백지) 인스턴스/서브에이전트가 뜸
2. 자기 [페르소나 파일] + [메모리 파일]을 컨텍스트로 로드  ← "기억 복원"
3. 일함
4. 남길 가치 있는 것만 메모리 파일에 기록  ← 다음번 부활용
5. 끝나면 컨텍스트 소멸 (메모리 파일은 영구)
```

연속성은 **파일**에 있다. 이미 `MEMORY.md` / `activeContext.md` / `session-log`가 쓰는 방식.

### 2-2. 메모리 예산 (필수 제약)
메모리 파일이 무한정 커지면 로드만으로 컨텍스트가 차서 직원이 느려진다. 따라서:
- 메모리는 **원문 덤프 X, 압축된 핵심(결정·선호·교훈)만**.
- 각 직원 메모리는 작고 집중되게 유지.
- 정기 가지치기는 **하네스 엔지니어** 담당.

### 2-3. 두 모자 분리 — 제안자 ≠ 판정자
- **제안자(리드)**: 기억O. 능동적으로 "뭘 만들자" 제안. → 메모리 가진 직원.
- **판정자(게이트)**: 컨텍스트0. 매번 백지. 작성자 편향 차단. → 일회용 서브에이전트 (백지는 *한계가 아니라 기능*).

### 2-4. 취향은 도현 전속
에이전트는 "안 깨짐"은 판정해도 "진짜 좋음"은 못 한다(관측됨: scatter 4→5 천장). 제안자는 후보 **≤3개**만 준비하고 **도현이 픽**. 에이전트의 "좋다" 사인 금지.

## 3. 실행 = 하이브리드 (항상 켜진 건 2개뿐)

| 직원 | 켜짐 | 모자 | Unity | 비고 |
|---|---|---|---|---|
| **리드 프로그래머 = 나** | 메인 세션 (항상, 허브) | 구현 | 만짐(직렬) | 디스패치·수거·Play |
| **PM/프로듀서** | 별도 터미널 인스턴스 (항상) | 조율 | 안 만짐 | backlog 소유, "다음 뭐" 끌기 |
| 게임 디자이너 | 일회용 서브 (필요시 승격) | 제안(기억O) | 정적 | 능동 기획. └시스템/맵/밸런스 |
| 기획 게이트 | 일회용 서브 | 판정(컨텍0) | Play 금지 | 흐름·주변 무결성 (진단①②) |
| 아트 디렉터 | 일회용 서브 (필요시 승격) | 제안(기억O) | 정적 | 룩·톤. 세부 2개: **월드룩 / UI** (라이팅은 룩 흡수) |
| 그래픽 게이트 | 일회용 서브 | 판정(컨텍0) | Play 금지 | 스샷만, 어색/깨짐 (진단③) |
| QA 리드 | 일회용 서브 | 검증 | Play(직렬) | 회귀 하네스 + 풀 루프 실플레이 |
| 하네스 엔지니어 | 일회용 서브 | 메타(B축) | — | incidents→룰→게이트 전환, 메모리 가지치기 |

> 디자이너·아트디렉터는 "끊김이 진짜 아프면" 나중에 켜진 인스턴스로 승격 가능. **시작은 2개만 켠다.**

### 왜 2개만 켜나 (오케스트레이션 역설 회피)
직군을 늘릴수록 디스패치·수거·라우팅 부담이 *허브(나)*에게 쏠려 병목을 줄이려다 키운다. 라이브 노드를 2개로 묶어 관리 비용을 최소화한다. 나머지는 필요할 때만 떴다 죽으므로 상시 관리 대상이 아니다.

## 4. 소통 = 공유 파일 버스 (직접 대화 X)

에이전트끼리 직접 주고받으면 *요약 한 통*으로 압축돼 디테일이 샌다. 그래서 **대화 대신 파일에 적어 넘긴다:**

| 파일 | 소유 | 역할 |
|---|---|---|
| `backlog.md` | PM | 우선순위 진실. 전원 읽음 |
| `docs/CONTROL.md` | PM/공용 | 관제탑 (이미 존재) |
| `tools/studio-dashboard/activity.jsonl` | hook 자동 | 누가 언제 뭐 했나 (이미 존재) |
| 디스패치 브리프 (작업당 1장) | PM | 현상/원인가설/완료조건. 디테일 통째 전달 |
| 게이트 판정 | 게이트 | **PASS/FAIL + 좌표** (느낌 X) |

PM은 머릿속으로 나한테 말하는 게 아니라 `backlog.md`·브리프에 적고, 나는 그 파일을 읽는다. 인스턴스가 달라도 파일은 안 사라지므로 손실 없는 소통.

## 5. 계급별 처리 (5홉 비용 방지)

모든 변경이 풀코스를 타지 않는다:

| 변경 종류 | 경로 |
|---|---|
| 오타·docs·hook-only | 나 혼자 |
| 한 시스템, 화면 안 건드림 | 나 + 기획 게이트 |
| **화면 / 배선 / 새 시스템** | 풀코스: PM 브리프 → 나 구현 → 게이트 둘 → QA 실플레이 → 커밋 |

## 6. 하루의 흐름 (예: "항구 ground 얼룩 fix")

```
1. PM(켜진) — CONTROL 게이트 잔여 읽음 → backlog 최상단 + 브리프 1장
        ↓ (backlog.md, brief 파일)
2. 나(메인) — 브리프 읽고 PlaceZoneGround 구현
        ↓
3. 그래픽 게이트(일회용, 컨텍0) — 스샷만 → PASS/FAIL+좌표
        ├ FAIL → 나 수정 → 재디스패치
        └ PASS ↓
4. 기획 게이트(일회용) — "다른 흐름 깼나? 빠진 단계?" → 판정
        └ PASS ↓
5. 나 — 커밋 (게이트 둘 통과해야 가능)
        ↓
6. PM — activity 갱신, backlog 내림, CONTROL 갱신
        ↓
7. 도현 — 대시보드로 결과 확인
```

켜진 건 둘(나·PM)뿐, 게이트는 필요할 때만 떴다 죽는다.

## 8. 단계적 도입 (한 번에 다 X = ExulMundi 회피)

- **Phase 1 (기반)**: 디렉터리 구조 + 게이트 2종 프롬프트 정식화(기존 ux-reviewer 계승) + `protocol.md`(소통 규약 + 계급 라우팅) + **PM 인스턴스 부팅**(페르소나 + backlog 소유 + 시작/종료 의례).
- **Phase 2**: 게임 디자이너 · 아트 디렉터 제안자 페르소나 + 대시보드 팀원 표시.
- **Phase 3**: QA 풀루프 페르소나 + 하네스 엔지니어 발전 루프(incidents→게이트 자동화 + 메모리 가지치기).

각 Phase 끝 = 실제로 그 직원을 한 번 굴려 작동 확인 후 다음.

사운드 · 내러티브 · 스팀 페이지/마케팅 → 데모 W5~W6 진입 시 추가. 지금은 린하게.

## 10. 정직한 잔여 리스크
- PM 인스턴스는 도현이 터미널 열고 살려둬야 함. 오래 켜면 압축 필요 → 메모리 예산 룰(2-2)이 방어.
- **Unity 1개 = Play 직렬 병목은 이 설계로 안 풀림.** 동시 Play 불가.
- 메모리 노후화 ×N → 하네스 엔지니어 정기 가지치기로 방어.
- 제안자에 기억을 주는 순간 컨텍스트0 순수성은 그 직원에게서 사라짐 → 그래서 *판정은 반드시 별도 백지 게이트*가 한다(2-3).

## 11. 성공 기준
- 화면/배선 변경이 PM 브리프 → 구현 → 게이트 둘 → 커밋 경로를 실제로 한 바퀴 돈다.
- 도현 부재 시 PM이 backlog를 능동 갱신해 "다음 뭐" 공백을 메운다.
- 직원 추가가 허브(나)의 상시 관리 부담을 늘리지 않는다(켜진 건 2개 유지).

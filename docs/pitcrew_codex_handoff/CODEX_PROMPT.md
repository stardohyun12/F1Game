# PitCrew 통합 구현 요청

F1Game의 PitCrew를 사용자가 감독하고 AI 팀과 직접 협업하는 게임 제작 작업실로 개선해 줘. 계획·문서·시각적 껍데기에서 끝내지 말고 현재 코드 조사 → 구현 → 검증 → 실제 실행본 확인까지 진행한다.

저장소: `D:\Github\F1Game`
주요 코드: `tools/studio-dashboard/`

이 문서와 REFERENCE_GUIDE.md를 읽고 references/의 PNG 네 장을 실제로 열어 확인한다. 참고 자료의 외형만 복제하지 말고 아래 사용자 흐름을 구현한다.

## 1. 제품 목표와 범위
사용자의 느낌과 상세 설명 → 참고 조사·분석 → 구체적 선택지 → 사용자 선택 → 작은 게임 구현 → 플레이·피드백 → 방향 확정 → 제작 확장 → 검증·출시 준비.

사용자는 전체 제작에 맡길 수도 있고 아트·조작감 등 특정 팀에 바로 요청할 수도 있다. 장기적으로 한 줄의 느낌과 상세 설명으로 제작을 진행하되, 이번에는 작은 실제 제작 과정 하나를 끝까지 연결한다. 처음부터 전체 출시 자동화나 범용 노드 편집기를 구현하지 않는다.

## 2. 현재 상태 조사와 작업 원칙
- AGENTS.md 등 적용 지침, Git 상태, 미커밋·미추적 변경을 확인하고 보존한다.
- 최신 코드와 운영 프로세스·로드된 버전을 확인한다. 이전 조사와 완료 보고를 현재 사실로 단정하지 않는다.
- 기존 파일 전달, 팀 대화, 이미지 입력·출력, 상태 표시 기능을 재사용하고 실제 동작을 확인한다.
- Codex·Claude 실행 방식, 모델 ID·추론 설정·권한, 세션 유지, 사용자 원문·추가 지침·도구 결과 전달을 조사한다. 직접 Codex보다 능력이 낮게 느껴지는 이유는 가설과 확인된 원인으로 구분한다.
- 개발은 우선 단일 Codex 에이전트로 수행한다. 제품의 멀티에이전트 실행과 개발 병렬화는 별개다.
- 전체 재작성, 사용자 변경 초기화, 자동 commit/push, 외부 공개 업로드, 임의 프로세스 종료는 하지 않는다.
- 되돌릴 수 있는 구현 선택은 스스로 결정한다. 운영 작업을 끊는 적용은 격리 검증 후 영향과 안전한 적용 절차를 알린다.

참고: 2026-10-17 초기 조사에서 일반 ZIP 다운로드 라우트·등록 누락과 디스크/실행본 기능 차이가 있었다. 이후 수정됐을 수 있으므로 반드시 현 상태를 확인한다. 자료는 docs/pitcrew-ui-reviews/ 아래에서 찾는다.

## 3. UI: 세 화면을 연결
### 제작 지도
팀 관계와 실제 작업 의존성을 구분해 보여준다. 현재 작업, 담당, 작업 중·입력 대기·의존 대기·실패·종료, 관련 결과·검증을 표시한다. 실제 위임과 전달 이벤트로 갱신하며 수동 상태판이나 가짜 진행률을 만들지 않는다. 팀을 누르면 기존 팀 작업실과 세션으로 이동한다.

### 팀 작업실
왼쪽 팀·세션 목록, 중앙은 팀의 작업 대상, 옆에는 대화·결과, 상세 로그는 펼칠 수 있게 구성한다. 요청 대상이 입력창에 명확히 보여야 한다. 팀 전환 시 입력 초안·대화 위치·세션을 유지한다. 팀 선택만으로 새 에이전트를 실행하지 않는다. 보내기·작업 중 추가 요청·취소의 차이를 명시한다.

### 결과·플레이
최신 결과, 버전 비교, 파일 다운로드, 지원되는 실행 동작, 검증·채택 상태를 표시한다. 결과에서 원래 작업과 대화로 이동한다. 참고 이미지·생성 시안·게임 적용 캡처·채택본을 구분한다. 파일 생성과 전달 가능, 팀별 완료와 전체 통합 완료를 구분한다.

시각 기준은 REFERENCE_GUIDE.md를 따른다. 한글 가독성, 초점·대비, 좁은 화면, 로딩·빈 상태·실패·복구도 구현한다. 모델·비용·상세 로그는 필요할 때 확인한다.

## 4. 실제 CLI 연결은 작은 시제품으로 검증
사용자는 실제 Codex·Claude Code 세션에 직접 입력하는 경험을 원한다. 로그를 터미널처럼 꾸미는 것으로 완료 처리하지 않는다.

현재 설치 버전과 환경에서 대화형 CLI 연결을 격리 시제품으로 검증한다. 한글 입력·붙여넣기, 승인·키보드 조작, 크기 변경, 취소·종료, 재연결과 같은 세션 유지, 직접 입력과 UI 요청 간 충돌을 확인한다.

CLI 모드와 기존 구조화 실행의 차이를 밝힌다. 두 방식이 같은 세션을 공유한다고 가정하거나 같은 요청을 중복 실행하지 않는다. 실제 CLI와 이미지 전달·상태 수집·자동화가 양립하는지 확인한 뒤 확대한다. 터미널 도입만으로 모델 성능이 개선된다고 주장하지 않는다.

## 5. 팀과 공통 맥락
논리적 팀: 전체 제작, 기획, 아트, 조작감, 프로그래밍·통합, 테스트.
첫 버전은 전체 제작·아트·조작감 흐름을 우선한다. 팀은 작업 영역이며 항상 여러 에이전트가 상주할 필요는 없다.

직접 팀에 요청한 작업도 전체 현황에 반영한다. 총괄이 모든 요청을 재작성해야만 실행되는 구조는 피한다.
공통 맥락은 목표·제약·채택한 방향, 팀 맥락은 상세 대화·실험, 팀 간 전달은 관련 결정·영향·산출물·원문 참조로 구분한다. 모든 대화를 매번 복사하거나 미채택 제안을 확정 방향으로 전파하지 않는다.

## 6. 아트: 이미지 양방향 작업
중앙에 이미지·지원되는 모델 미리보기와 전후 비교, 옆에 이미지 포함 대화, 자료 목록에 참고·시안·적용 캡처·채택본, 접을 수 있는 영역에 CLI를 둔다.

사용자는 이미지 붙여넣기·드래그·선택, 여러 참고 자료의 용도 설명, 특정 이미지 버전 선택과 수정 요청을 할 수 있어야 한다. 가능한 범위에서 영역 표시와 의견을 연결한다.

AI는 첨부 이미지를 실제로 읽고, 생성·수정 결과를 답변과 결과 목록에 표시한다. 수정 대상 이미지 버전·영역·설명이 다음 실행에 함께 전달돼야 한다. UI에 이미지가 보인다고 모델이 봤다고 간주하지 말고 실제 입력 경로를 검증한다.

이미지 생성·편집·Blender는 실제 설치·권한·연결을 확인해 사용한다. 지원되지 않는 기능은 명확히 표시한다. 파일 경로만 받은 상태에서 이미지를 봤다고 하거나 이미지 생성 도구 없이 생성했다고 보고하지 않는다.

실제 흐름: 참고 → 소수의 다른 시안 → 선택 → 에셋 하나 제작 → Unity 적용 → 같은 카메라로 비교 → 채택 → 확장. 컨셉 이미지가 좋다는 이유만으로 대량 에셋 제작을 시작하지 않는다.

## 7. 조작감: 플레이와 피드백
“더 경쾌하게”, “회전 시작이 답답하다”를 조정 가능한 가설로 바꾸고 작은 변경으로 시험한다. 변경 값·기대 효과·테스트 조건·전후 버전·플레이 피드백·채택 여부를 연결한다.
실행 가능한 버전이나 실제 가능한 실행 안내를 제공한다. 임베드 미지원 상태를 숨기지 않는다. 캡처나 녹화만으로 조작감이 검증됐다고 하지 않는다.

## 8. 산출물과 상태
기존 등록·다운로드 기능을 재사용하되 실제로 검증한다. 프로젝트·팀·작업·실행·버전과 산출물을 연결하고, 서버가 발급한 ID·URL로 표시한다. 모델이 로컬 경로나 주소를 추측하게 하지 않는다.

이름·크기·형식·시각·해시를 기록하고, 등록 후 변경 정책을 명확히 한다. 한글·공백 파일명, 삭제·변경·만료, 경로 탈출·프로젝트 경계·심볼릭 링크 등을 확인한다. 임의 로컬 파일 전체를 제공하는 API는 만들지 않는다.

실행 상태와 결과 상태를 구분한다: 실행 중/대기/실패·종료, 결과 생성, 기술 검증, 사용자 채택, 통합 확인. 모든 작업에 불필요한 수동 승인을 강제하지 않는다.

## 9. 멀티에이전트가 필요한 경우
독립 작업 병렬 처리, 서로 다른 시안 비교, 구현·검증 분리에 사용한다. 간단한 수정은 단일 담당이 끝낸다. 검증 담당의 세션·수정 권한 등 실제 독립성도 확인한다.
동일 파일·씬·Unity Editor 동시 수정은 소유권·대기열 등으로 막는다. 전달을 추적하고 반복·시간 한도와 취소를 지원한다. 순환 호출을 방지한다.

## 10. 이번 첫 완성 흐름
F1Game의 작은 테스트 구간을 사용하고 기존 게임 작업에 영향을 줄 변경은 격리한다.
1. 전체 제작에 장면·주행 느낌 입력.
2. 아트 팀에 참고 이미지 전달.
3. 실제 이미지 입력 처리 후 시안 또는 수정 결과 반환.
4. 특정 결과에 사용자 피드백·채택.
5. 조작감 팀에 직접 수정 요청.
6. 작은 게임 구간에 통합.
7. 적용 캡처·파일·플레이 결과 확인.
8. 채택한 방향을 다음 작업에 재사용.

사용자 선택·플레이 평가는 자동으로 꾸며내지 않는다. 필요한 경우 실제 결과를 먼저 제시하고 질문하며, 독립적으로 가능한 개발·테스트는 계속한다. 외부 도구 부재로 막히면 가능한 부분까지 구현하고 정확한 한계와 연결 절차를 남긴다.

## 11. 검증과 보고
- 이미지 실제 입력, 생성 결과 표시, 버전·영역을 포함한 후속 요청.
- 팀 전환 후 대상·세션·초안 유지.
- 파일 카드 클릭 후 실제 저장 파일과 원본 SHA-256 일치.
- 실패·취소·재연결, 실제 실행본 반영.
- 주요 화면 캡처와 가독성·밀도·정렬·초점·좁은 화면 검토.
- fixture 화면, HTTP 확인, 실제 브라우저, 실제 AI·Unity 검증을 구분. 브라우저 제어 불가 시 미검증을 명시.

가능한 범위에서 동일 초기 상태·작은 과제·모델·추론 설정으로 직접 Codex / PitCrew 단일 / PitCrew 멀티를 비교한다. 완료 시간, 재설명·사용자 개입, 재작업, 사용량을 기록한다. 무제한 실행하거나 비용·측정값을 만들지 않는다. 한 번의 결과로 일반적 우열을 주장하지 않는다.

사용자가 배울 수 있도록 결과 옆에 “무엇을 바꿨고 왜 달라졌는지”를 펼쳐 볼 수 있게 하되, 설명 때문에 기본 작업을 막지 않는다.

최종 보고는 구현된 흐름·화면, 실제 검증 결과, 예시 데이터로만 확인한 범위, 제한, 운영 반영 여부, 짧은 시작 방법을 포함한다. 일반 파일 전달이 완성되면 최종 검토 자료도 그 경로로 검증한다.

현재 상태와 목표의 차이를 짧게 정리하고 구현을 시작해 줘. 기능 껍데기를 늘리기보다 첫 사용자 흐름이 실제로 이어지도록 완성해 줘.
